# M1 — settings and attribution UI

Users define the header set and the feature rules inside aoe, and see what each session resolves
to. Depends on M0 (a header that provably arrives).

## Tasks

Priorities: `P0` blocks the acceptance below, `P1` is needed to use the milestone for real (or by
the next one), `P2` may slip. Legend: `plan/README.md`.

1. **[P0] Manifest update, one change.** Add `capabilities = ["runtime.worker", "session.read", "net"]`,
   `[[commands]] id = "status"`, `[[ui]] slot = "row-badge"` and `slot = "pane"`, and the
   `[[settings]]` entries from the table below. Widening capabilities forces a re-approval
   prompt, so do it once, with the final set.
2. **[P0] Worker.** `worker/main.py`: stdio JSON-RPC, dispatch on the trailing segment of
   `plugin.dev.oozut.llm-tags.<cmd>`, `-32601` for unknown, never reply without `id`. Import the
   M0 resolver; do not reimplement it.
3. **[P0] Settings UI.** `headers` as an `object_list` (`item_id_key = "header"`) with add/remove
   and the validation from acceptance 4; `rules` as `object_list` (`item_id_key = "match_value"`,
   caveat in `parameters.md` §3) with `match_kind` as an enum; `session_tagging` enum;
   `feature_tag` with `per_project = true`; `session_signature` + `signing_key` if open #8 lands
   in M1.
4. **[P0] Row badge.** `ui.state.set`, slot `row-badge`: the resolved default header value, tone
   `warn` when unwired. Truncate, never wrap.
5. **[P1] Pane.** Slot `pane`: each enabled header → its variable → its resolved value; adapter
   and wired state; substrate-specific timing text ("applies on next launch" vs "on next
   container start"); copyable `setup --print`.
6. **[P1] `status` command.** Resolved values for every session via `sessions.list`, `--json`
   respected. Same numbers as the hook (shared resolver test).
7. **[P1] Shared-resolver test.** One test asserting `hook` output equals `status` output for the
   same session, and `value <header>` equals the matching line. This is what stops the worker and
   the CLI from drifting.
8. **[P2] Lifecycle cache.** Invalidate on `session.lifecycle.changed` (`api_version 19`), not on
   a timer.

## Acceptance → evidence

| # | Check | Evidence |
|---|---|---|
| 1 | rule edit changes the badge next launch, no file edit | screenshot/e2e trace: settings → badge, config.toml untouched |
| 2 | project `feature_tag` overrides global, editable in the project form | two projects, different tags, same global default |
| 3 | unwired harness shows a visibly different badge | badge with `warn` tone next to a wired one |
| 4 | validation rejects bad header name, bad value grammar, over-long value | three rejected saves with the message shown |
| 5 | enabling a second header adds exactly one env var + one mapping line | `setup --print` diff, before/after |

## Done when

- All P0 tasks are complete. P1 tasks (pane, `status`, shared-resolver test) may follow in the
  same release and are listed as open in `plan/README.md` until they land.
- No setting added at M1 requires a hand-edit of `config.toml` to change its value.
- Badge and `doctor` agree on wired/unwired for the same session (the pane, once it lands as P1,
  agrees with both).

## Risks

- **Two resolvers.** The worker and the CLI both answer "what does this session resolve to". Keep
  one implementation and one test, or they drift silently.
- **Capability widening.** Adding `net` later costs the user another approval prompt; take it now
  if M2/M3 will need it.
