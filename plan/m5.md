# M5 — per-request values and activity

The gap this closes: M0 gives a session a header set **once per launch**. A harness reads its
config, caches the values it finds there, and every request for the life of that process carries
the same bytes. So a tag edited while a session runs, and anything that says what the session is
*doing* rather than what it *is*, cannot be delivered by the launch hook at all.

The route is not a proxy (`plan/roadmap.md` §5 records why that stays out): a harness that loads
code from its config directory runs that code in-process, and pi re-emits a
`before_provider_headers` event before **each** model request. An extension the plugin ships and
the user explicitly approves can therefore set the header per request, with no listener, no new
capability, and nothing in the request path.

That extension is code running inside the agent, so it is opt-in twice — see
`src/harness_extension.rs` and the `harness_extension` setting — and clause 1 of the acceptance
below is the whole point of the milestone, not a nicety.

## Tasks

Priorities: `P0` blocks the acceptance below, `P1` is needed to use the milestone for real (or by
the next one), `P2` may slip. Legend: `plan/README.md`.

The numbered list is the *detail*; the task table below it is the *index* (ID, priority, lane,
dependencies, size, output). Number and ID must agree.

1. **[P0] Consent machinery.** `harness_extension` setting (intent), receipt file with the
   artefact's sha256 + disclosure version (approval), the refusal reasons, `extension
   status|enable|disable`, one `doctor` line per harness that can take an extension, and refusal
   tests for every state. No listing and no receipt ⇒ nothing is written, no warning at launch.
2. **[P0] The artefact and its installation.** `harness/pi.ts` compiled into the binary
   (`src/artifacts.rs`), written into the session's config copy only on an allowed verdict, with
   `extensions/` materialised as a real directory whose other entries are the user's own,
   `AOE_LLM_TAGS_LIVE` exported, and `sessions/<id>/live.json` written from the values the launch
   already resolved. A changed artefact or an older disclosure installs nothing.
3. **[P1] Live activity.** The worker rewrites `live.json` when a session's tags change (not only
   at launch), and flips `enabled` on revoke, so a running session's next request reflects it.
4. **[P1] Activity vocabulary.** `activity:*` reserved keys (`explore`, `plan`, `code`, `test`,
   `debug`, `review`, `docs`, `ops`, `idle`) with a lucide icon and a tone each; rendered as a
   badge on the row, in the pane and in the page legend; text fallback everywhere the icon cannot
   render. The icon is presentation and never enters the payload.
5. **[P1] Declaring activity — a skill, not a heuristic.** The agent should keep the activity
   current *by itself*, so the delivery is a **skill** (`skills/aoe-activity/SKILL.md` in the
   session's config copy): pi discovers it under `PI_CODING_AGENT_DIR` (verified), announces it in
   the system prompt, and its instructions are "run `aoe-llm-tags activity <name>` as the work
   moves between phases". The command is the existing per-session edit, so nothing new decides
   what a target carries, and a session whose harness has an approved extension reaches its next
   request. A human keeps the last word: the pane offers every value as a row (the session view
   and the TUI), the page offers buttons, and the row badge shows the current one — the last
   writer wins, whichever side it is. No tool-name heuristic: an inferred activity would be a
   guess sent downstream, which is a claim the plugin should not make on its own. The skill is
   part of the same approved file set, so the disclosure names both files and its version moves
   with them.
6. **[P2] Second harness.** opencode's plugin API needs one probe before a row gets an
   `extension_artifact`; until then every other harness stays launch-scope, which is honest.
7. **[P2] Docs polish.** `docs/header-contract.md` §Per-request, the README paragraph, the
   `plan/roadmap.md` §5 rewrite.

## Evidence

**A tag edited mid-session reaches the next request, in one process (2026-11-07).** A throwaway
app dir, a fake `aoe`, the real CLI and pi 1.4.0 against `tools/header-sink.py`:

```
$ aoe-llm-tags extension enable pi --print        # the disclosure, then:
$ aoe-llm-tags extension enable pi --accept d653f348…
approved: pi (sha256 d653f3485238, disclosure v1)
$ aoe-llm-tags hook
PI_CODING_AGENT_DIR=/tmp/m5e2e/config/agent-of-empires/sessions/S-dyn1/pi
AOE_LLM_TAGS_LIVE=/tmp/m5e2e/config/agent-of-empires/sessions/S-dyn1/live.json
```

`pi --mode rpc`, two prompts, one process. Between them: `tag --set activity:test` and the worker's
rewrite of `live.json`. What the sink received:

```
/v1/chat/completions | aoe,
/v1/chat/completions | aoe,activity:test
```

The second request differs, no process restarted, and the value is the one the resolver produced —
the extension only repeated it. The same edit → `live.json` path is covered by a worker test, and
`extension disable` flips `enabled` in the same file so a running session stops on its next
request.

**The agent keeps the activity current, and the carriers reach the model (2026-11-08).** The same
real-pi arrangement, with the session copy's `skills/aoe-activity/SKILL.md` and `APPEND_SYSTEM.md`
in place, one `pi -p` request captured at the sink. The system prompt contains both carriers:

```
<addendum>
## Session activity (Agent of Empires)
… run `"${AOE_LLM_TAGS_BIN:-aoe-llm-tags}" activity <word>` when a phase starts — not on every
tool call — where word is one of explore, plan, code, test, debug, review, docs, ops, idle.
</addendum>

<skills>
…
  <skill><name>aoe-activity</name><description>Keep this session's Agent of Empires activity
  current…</description><path>…/skills/aoe-activity/SKILL.md</path></skill>
```

Two carriers on purpose: the skill is advertised and loaded on demand, the reminder is always in
the prompt. `aoe-llm-tags activity testing` then writes `activity:test` — the label is accepted, the
key is stored — and the worker refreshes `live.json`, so the same phase reaches the badge, the pane,
the page and the next request.

**It is a first-class AoE skill, not a stray file (2026-11-08).** Written into AoE's managed store,
the skill is what `aoe skill list` and the Skills page report — the integration AoE documents for its
own packages, rather than a private file in a harness's config:

```
$ XDG_CONFIG_HOME=<app dir parent> aoe skill list
DIRECTORY                SOURCE               NAME
aoe-activity             aoe-managed          aoe-activity
$ aoe skill view aoe-activity            # frontmatter + body, as any managed skill
```

That also means a user can `aoe skill edit aoe-activity`, adopt it as their own (in which case the
marker is gone and a later release leaves it alone), or share it to the agents AoE knows with
`aoe skill sync`. The session copy is what pi actually loads; the managed entry is discoverability.

**Digest of the shipped bundle:** `0228e63707ff451a4890a3a94d24f8a6e8b5b3c157524fdf903a73073dbadb75`
for `pi` (session scope; `harness/pi.ts`, `harness/skills/aoe-activity/SKILL.md`,
`harness/activity.append.md`) and `069d8952700ca4fbd2729d319dd522a091fe3c2a875f368269e0285576e16a08`
for `claude` (user scope; the same skill and reminder, placed under `~/.claude`), both pinned by
`tests/extension.rs`; a change fails the build until the constant and `DISCLOSURE_VERSION` are
updated deliberately. The digest covers the **destination** as well as the bytes
(`carrier:{scope}` then `{path} {sha256}` per part), because where a file goes is part of what the
user approved — moving a skill is a new grant even with identical contents. The receipt stores this
bundle digest, so adding a file is a re-approval, as is rewording the skill. Disclosure version 3
is the one that distinguishes the two carrier scopes.

### Two carrier scopes, one mechanism

Only `pi` and `vibe` read a config directory the hook can build per session. For everyone else
"this session's activity" can only reach the agent through the harness's own configuration under
`$HOME`, which is a wider grant — so it is a different disclosure, not a footnote to the same one.
`carrier_scope` in `adapters.toml` decides, and `carrier()` falls back to `session` when a row has
an `extension_artifact`, to `user` when it has a user path, else `None` (refused by name).

| | `session` | `user` |
|---|---|---|
| rows | `pi`, `vibe` | `claude`, `codex`, `opencode`, `hermes`, `gemini`, `droid`, `qwen`, `kiro` |
| destination | `sessions/<id>/<harness>/…` | `~/.<harness>/skills/aoe-activity/SKILL.md` + a block in `~/.<harness>/CLAUDE.md` (or `AGENTS.md`, `GEMINI.md`, `SOUL.md`, `QWEN.md`, kiro's steering doc) |
| ownership | the copy is entirely ours | the skill directory is ours; the instruction file is the user's, and only the block between `<!-- aoe-llm-tags:begin -->` and `<!-- aoe-llm-tags:end -->` is written |
| removal | the copy's parts go; a directory that held only our file goes with it | the skill goes (only with the managed marker), the block is stripped, and a file the block was alone in is deleted |
| when it lands | next launch | at approval, immediately — a user-scope write is not something a launch can silently do |

`kiro` ships no skill: it has no skill loader, so its carrier is the steering document alone —
shipping a skill nothing reads would be a lie. A row with no hook, no skill root and no instruction
file is refused by name (`no_destination`) with launch-time tags and nothing else; that is
`cline` and `openclaw` today.

## Acceptance

1. **Nothing is installed without the user's approval, and "installed" is said out loud.** With an
   empty `harness_extension` a launch writes no code anywhere and says nothing; with the setting
   set but no receipt it writes nothing and warns with the command that fixes it; with both it
   writes exactly one file and the `doctor` line, the pane and the manifest description all say
   that this is code running inside the agent.
2. **The approval is durable and specific.** A plugin update that does not change the artefact,
   a reinstall, a harness upgrade or an unrelated config edit all leave it working; a change to
   the artefact's bytes or a bumped disclosure version installs nothing until it is re-approved;
   approving one harness approves no other.
3. **A user-scope write never rewords a file the user owns.** For a `user` row the skill is a
   directory of its own and the reminder lives between two markers; everything outside them is
   byte for byte what it was, a second approval is the same file rather than a second block, and a
   revoke restores the file exactly — deleting it only if the block was all it held. A skill
   directory without the managed marker is somebody's own and is never overwritten.
4. **The user's own session config is untouched.** The session copy's `extensions/` directory is a real
   directory of links to the user's entries plus this plugin's file; the user's `extensions/`
   directory is byte-identical afterwards, and a session that stops being approved gets an empty
   directory again rather than a stale file.
5. **Per request, not per launch.** With an approved extension, two requests in one agent process
   carry two different values, and no process restart is involved. The values are the ones the
   plugin resolved; the extension mints nothing (proved by a live file that carries the launch's
   resolution, and by the fail-open path leaving launch-time headers in place).
6. **Revocation is immediate enough and honest.** `extension disable <harness>` stops the next
   launch from installing the file; a session already running stops sending dynamic values on its
   next request. `doctor` reports the state before, during and after.
7. **Sandboxed sessions stay unsupported, explicitly.** `doctor` keeps saying sandboxed sessions
   send no headers, and no extension is staged into a sandbox (aoe copies only the user's own
   `extensions/`).
