# M5 — per-request values and activity

The gap this closes: M0 gives a session a header set **once per launch**. A harness reads its
config, caches the values it finds there, and every request for the life of that process carries
the same bytes. So a tag edited while a session runs, and anything that says what the session is
*doing* rather than what it *is*, cannot be delivered by the launch hook at all.

The route is not a proxy (`plan/roadmap.md` §5 records why that stays out): a harness that loads
code from its config directory runs that code in-process, and pi re-emits a
`before_provider_headers` event before **each** model request. An extension the plugin ships and
the user explicitly approves can therefore set the header per request, with no listener, no new
capability, and nothing in the request path.

That extension is code running inside the agent, so it is opt-in twice — see
`src/harness_extension.rs` and the `harness_extension` setting — and clause 1 of the acceptance
below is the whole point of the milestone, not a nicety.

## Tasks

Priorities: `P0` blocks the acceptance below, `P1` is needed to use the milestone for real (or by
the next one), `P2` may slip. Legend: `plan/README.md`.

The numbered list is the *detail*; the task table below it is the *index* (ID, priority, lane,
dependencies, size, output). Number and ID must agree.

1. **[P0] Consent machinery.** `harness_extension` setting (intent), receipt file with the
   artefact's sha256 + disclosure version (approval), the refusal reasons, `extension
   status|enable|disable`, one `doctor` line per harness that can take an extension, and refusal
   tests for every state. No listing and no receipt ⇒ nothing is written, no warning at launch.
2. **[P0] The artefact and its installation.** `harness/pi.ts` compiled into the binary
   (`src/artifacts.rs`), written into the session's config copy only on an allowed verdict, with
   `extensions/` materialised as a real directory whose other entries are the user's own,
   `AOE_LLM_TAGS_LIVE` exported, and `sessions/<id>/live.json` written from the values the launch
   already resolved. A changed artefact or an older disclosure installs nothing.
3. **[P1] Live activity.** The worker rewrites `live.json` when a session's tags change (not only
   at launch), and flips `enabled` on revoke, so a running session's next request reflects it.
4. **[P1] Activity vocabulary.** `activity:*` reserved keys (`explore`, `plan`, `code`, `test`,
   `debug`, `review`, `docs`, `ops`, `idle`) with a lucide icon and a tone each; rendered as a
   badge on the row, in the pane and in the page legend; text fallback everywhere the icon cannot
   render. The icon is presentation and never enters the payload.
5. **[P1] Declaring activity.** `set_activity` command in the extension, `AGENTS.md` snippet, and
   a muted heuristic fallback (tool name → activity) for sessions that declare nothing.
6. **[P2] Second harness.** opencode's plugin API needs one probe before a row gets an
   `extension_artifact`; until then every other harness stays launch-scope, which is honest.
7. **[P2] Docs polish.** `docs/header-contract.md` §Per-request, the README paragraph, the
   `plan/roadmap.md` §5 rewrite.

## Acceptance

1. **Nothing is installed without the user's approval, and "installed" is said out loud.** With an
   empty `harness_extension` a launch writes no code anywhere and says nothing; with the setting
   set but no receipt it writes nothing and warns with the command that fixes it; with both it
   writes exactly one file and the `doctor` line, the pane and the manifest description all say
   that this is code running inside the agent.
2. **The approval is durable and specific.** A plugin update that does not change the artefact,
   a reinstall, a harness upgrade or an unrelated config edit all leave it working; a change to
   the artefact's bytes or a bumped disclosure version installs nothing until it is re-approved;
   approving one harness approves no other.
3. **The user's own config is untouched.** The session copy's `extensions/` directory is a real
   directory of links to the user's entries plus this plugin's file; the user's `extensions/`
   directory is byte-identical afterwards, and a session that stops being approved gets an empty
   directory again rather than a stale file.
4. **Per request, not per launch.** With an approved extension, two requests in one agent process
   carry two different values, and no process restart is involved. The values are the ones the
   plugin resolved; the extension mints nothing (proved by a live file that carries the launch's
   resolution, and by the fail-open path leaving launch-time headers in place).
5. **Revocation is immediate enough and honest.** `extension disable <harness>` stops the next
   launch from installing the file; a session already running stops sending dynamic values on its
   next request. `doctor` reports the state before, during and after.
6. **Sandboxed sessions stay unsupported, explicitly.** `doctor` keeps saying sandboxed sessions
   send no headers, and no extension is staged into a sandbox (aoe copies only the user's own
   `extensions/`).

## Done when

- T01 and T02 are complete: every state in §Acceptance 1 and 2 is covered by a test that runs the
  real CLI in a throwaway tree, including the two that install nothing.
- A pi session launched by aoe carries a tag value that changed after launch, with the file, the
  receipt and the `doctor` line all agreeing about what was installed.
- `plan/roadmap.md` §5 no longer defers per-request tagging to an upstream change for pi, and
  still says plainly which harnesses remain launch-scope and why.
